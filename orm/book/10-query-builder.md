`find` and `all` cover two queries. The third most common is "these rows, filtered, sorted, a
page at a time", and its filter changes with the request: a tag if the client sent one, a
price range if it sent that, both or neither. Writing that SQL by hand means assembling a
string and a parameter list in step, numbering each `$n` correctly, which is exactly the code
where injection bugs and off-by-one parameter errors live.

A query builder assembles it for you, from typed pieces. The derive already knows every column
and its Rust type, so it can generate a constant per column, `Product::PRICE_CENTS`, that knows
both. A filter built from it, `Product::PRICE_CENTS.gt(1_000)`, can only take an `i64`, and a
mistake is a compile error at the call. The builder numbers the parameters, keeps the values
out of the SQL, and stays small enough to read in one sitting.

**In this chapter you will learn:**

- what a query builder should type (columns and values) and what it should leave to SQL
- how `Table` generates a `Column<M, T>` constant per field, and what `PhantomData` does there
- how expressions become SQL with numbered parameters and an owned parameter list
- ordering, limits and keyset pages
- which mistakes fail to compile, shown with UI tests
- the escape hatch: raw SQL, inside a filter or instead of the builder

## 10.1 What to type

Plan:
- Typed: the column (it belongs to this model) and the value (it has the column's type).
- Left to SQL: functions, joins, subqueries; the builder accepts a raw fragment with its
  parameters instead of modelling them.

## 10.2 Column constants

Plan:
- `Product::PRICE_CENTS: Column<Product, i64>`, an inherent constant generated from each field,
  as visible as the field; only the quoted name is stored. `T` is what the column holds: the
  `try_from` source type, `serde_json::Value` for a `json` field (the expansion test
  `columns.expanded.rs`, printed).
- A **Rust refresher** on `PhantomData<fn() -> (M, T)>`: a zero-sized marker that makes the
  type carry the model and the value type, and why `fn() -> …` (always `Send`, `Sync`, `Copy`).
- An inherent constant shadows a trait constant of the same name: `Product::VERSION` is the
  column, `<Product as Table>::VERSION` the metadata (§12 #35).
- `Value<T>`: what a condition accepts. Measured on the compiler, not guessed: one widening
  impl (`i32` for `i64`) makes integer literals fall back to `i32` and `3_000_000_000` fail to
  compile, so shelf converts no numbers (§12 #34).

## 10.3 Expressions

Plan:
- `eq`, `ne`, `lt`, `le`, `gt`, `ge`, `between` and `any` (`= ANY($n)`, one array) on every
  column; `like` only on text columns, `is_null` only on `Option` columns, `contains` (`@> $n`,
  a one-element array) only on array columns: impl blocks on `Column<M, String>`,
  `Column<M, Option<T>>`, `Column<M, Vec<E>>`. `and`, `or`, and `!` through `std::ops::Not`
  (a method called `not` trips clippy's `should_implement_trait`).
- An expression tree rendered at each call into SQL text and a parameter list by one function
  that writes both (`render.rs`), so the `$n` and the list cannot drift; parentheses where an
  `OR` sits inside an `AND`. The rendered SQL printed (`query.sql()`, `query.params()`).
- How PostgreSQL types each parameter (§12 #36): against a domain column, `=`, `= ANY` and
  `LIKE` take the base type, so `&str` works there.

## 10.4 Owned parameters

Plan:
- The query owns its values (`Box<dyn ToSql + Sync + Send>`), so it can be built in one
  function and run in another, across an await and inside `tokio::spawn` (a test does).
- The cost: one allocation per parameter; nothing compared with a round trip.
- Its methods are inherent `async fn`s: unlike `async fn` in a trait, their futures leak their
  auto traits, so they are `Send` for a generic executor (a compile-only check in the tests).

## 10.5 Order, limit and pages

Plan:
- `order_by(Product::SKU.asc())`, `limit`, `offset` (parameters, so a page size is not a new
  statement); key order when nothing is ordered; `first` (`LIMIT 1`); `count` and `exists` on
  the same filter, ignoring order and paging.
- Keyset pagination with `after(Product::SKU, last)`: `"sku" > $n`, ordered by the column first
  (main book Chapter 9's recommendation), and why `offset` gets slower page by page.

## 10.6 What fails to compile

Plan:
- The captured errors of `tests/ui/query.stderr` (§12 #41): `&str` and `i32` for a `bigint`
  column, in `Value`'s words; another model's column, first as rustc reported it through
  `impl Into<Expr<M>>` ("… but trait `From<Raw<Product>>` is implemented") and then through
  the `Condition<M>` trait ("`Expr<Order>` is not a condition on `Product`"), the change that
  reading the error made; `like` on an `i64`, `is_null` on a `String`, `contains` on a text.
- What still fails at run time: a raw fragment, and a column whose type changed in the
  database (Chapter 13).

## 10.7 The escape hatch

Plan:
- `fetch_all::<T>` with hand-written SQL, as always.
- `Expr::raw(r#"lower("name") = lower($1)"#).bind("tee")` inside a filter: its `$1…` renumbered
  among the builder's by a scanner that skips quoted text, `$tag$` strings and comments
  (`render.rs`, unit tested), and a panic where the fragment is used if it refers to a value it
  was not given (it would silently take another condition's).

## Side by side

A filtered, sorted page: by hand (stockroom's keyset `page`) · shelf
(`Product::query().filter(…).order_by(…).limit(20).all(&db)`) · diesel
(`products.filter(price_cents.gt(1000)).order(sku.asc()).limit(20)`, check).

## In stockroom

`page` in [stockroom/src/repo/products.rs](../../stockroom/src/repo/products.rs): the
optional tag filter written as `($2::text IS NULL OR tags @> ARRAY[$2])`, which a builder
replaces with a filter that is simply absent.

## Claims

- Opinion: a query builder earns its place for optional filters; for fixed queries, plain SQL
  is clearer.
- Docs: PostgreSQL's array operators (`@>`, `= ANY`).

## When not to use the builder

- Reports, aggregates, CTEs, window functions: SQL with a `FromRow` struct.
- A fixed query run often: a hand-written statement caches as one statement; each filter
  shape is a different statement, cached once per shape on a deadpool connection.
