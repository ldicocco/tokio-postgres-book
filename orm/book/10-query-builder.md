`find` and `all` cover two queries. The third most common is "these rows, filtered, sorted, a
page at a time", and its filter changes with the request: a tag if the client sent one, a
price range if it sent that, both or neither. Writing that SQL by hand means assembling a
string and a parameter list in step, numbering each `$n` correctly, which is exactly the code
where injection bugs and off-by-one parameter errors live.

A query builder assembles it for you, from typed pieces. The derive already knows every column
and its Rust type, so it can generate a constant per column, `Product::PRICE_CENTS`, that knows
both. A filter built from it, `Product::PRICE_CENTS.gt(1_000)`, can only take an `i64`, and a
mistake is a compile error at the call. The builder numbers the parameters, keeps the values
out of the SQL, and stays small enough to read in one sitting.

**In this chapter you will learn:**

- what a query builder should type (columns and values) and what it should leave to SQL
- how `Table` generates a `Column<M, T>` constant per field, and what `PhantomData` does there
- how expressions become SQL with numbered parameters and an owned parameter list
- ordering, limits and keyset pages
- which mistakes fail to compile, shown with UI tests
- the escape hatch: raw SQL, inside a filter or instead of the builder

## 10.1 What to type

Plan:
- Typed: the column (it belongs to this model) and the value (it has the column's type).
- Left to SQL: functions, joins, subqueries; the builder accepts a raw fragment with its
  parameters instead of modelling them.

## 10.2 Column constants

Plan:
- `Product::PRICE_CENTS: Column<Product, i64>` (proposed names), generated from each field;
  the quoted column name inside.
- A **Rust refresher** on `PhantomData<(M, T)>`: a zero-sized marker that makes the type
  carry the model and the value type.

## 10.3 Expressions

Plan:
- `eq`, `ne`, `lt`, `le`, `gt`, `ge`, `between`, `like`, `is_null`, `any` (`= ANY($n)` with a
  `Vec`), `contains` (`@>` for arrays); `and`, `or`, `not`.
- An expression tree rendered once into SQL text and a parameter list, numbering `$1…$n` as it
  goes; the rendered SQL printed in the chapter.

## 10.4 Owned parameters

Plan:
- The query owns its values (`Box<dyn ToSql + Sync + Send>`, proposed), so it can be built in
  one function and run in another, across an await.
- The cost: one allocation per parameter; nothing compared with a round trip.

## 10.5 Order, limit and pages

Plan:
- `order_by(Product::SKU.asc())`, `limit`, `offset`; `count` and `exists` on the same filter.
- Keyset pagination with `after(Product::SKU, last)` (main book Chapter 9's
  recommendation), and why `offset` gets slower page by page.

## 10.6 What fails to compile

Plan:
- A wrong value type (`Product::PRICE_CENTS.eq("x")`), a column of another model in a
  `Product` query: UI tests and their captured errors.
- What still fails at run time: a raw fragment, and a column whose type changed in the
  database (Chapter 13).

## 10.7 The escape hatch

Plan:
- `fetch_all::<T>` with hand-written SQL, as always.
- A raw fragment inside a filter, with its own parameters renumbered by the builder.

## The programs

- `run` (proposed): a filtered, sorted page against a temporary table.
- `run`: the rendered SQL and its parameters printed for three filters.
- `run`: keyset pages until the end.

## Side by side

A filtered, sorted page: by hand (stockroom's keyset `page`) · shelf
(`Product::query().filter(…).order_by(…).limit(20).all(&db)`, proposed) · diesel
(`products.filter(price_cents.gt(1000)).order(sku.asc()).limit(20)`, check).

## In stockroom

`page` in [stockroom/src/repo/products.rs](../../stockroom/src/repo/products.rs): the
optional tag filter written as `($2::text IS NULL OR tags @> ARRAY[$2])`, which a builder
replaces with a filter that is simply absent.

## Claims

- Opinion: a query builder earns its place for optional filters; for fixed queries, plain SQL
  is clearer.
- Docs: PostgreSQL's array operators (`@>`, `= ANY`).

## When not to use the builder

- Reports, aggregates, CTEs, window functions: SQL with a `FromRow` struct.
- A fixed query run often: a hand-written statement caches as one statement; each filter shape
  is a different statement (the open question below).
